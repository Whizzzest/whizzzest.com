# 仓库同步方案（pan-nie/whizzzest.com → Whizzzest/whizzzest.com 单向镜像）

> 2026-10-14 业主拍板立项。业主报「现在对于我的企业仓库也要同步，你看如何自动化处理？」
> 本文件为实施依据；落地过程与线上核验记入 [上线记录.md](./上线记录.md)，任务声明见 [任务看板.md](./任务看板.md)。

| 项 | 结果 |
| --- | --- |
| 权威仓库（开发 + 部署） | `git@github.com:pan-nie/whizzzest.com.git`（个人号 pan-nie，SSH） |
| 企业仓库 | `git@github.com:Whizzzest/whizzzest.com.git`：**公开**、默认分支 `main`、org `Whizzzest`（创建于 2026-10-02）、业主权限 ADMIN、无分支保护 |

| 企业仓库的 CI | 已带一份 `deploy.yml`，但该仓库**没有任何 secrets** → `CLOUDFLARE_API_TOKEN` 为空，实测 5 个部署步骤全部 `skipped`（**当时没有双重部署**） |

**风险**：两个仓库若都配上 `CLOUDFLARE_API_TOKEN`，就会各自部署同一套 Worker（并发部署打架，D1 迁移/R2 上传更危险）。所以「能部署的仓库」必须唯一。

## 二、业主拍板（2026-10-14）

1. **权威仓库**：个人仓库 `pan-nie/whizzzest.com` 继续当唯一权威 + 唯一部署点；企业仓库纯镜像。
2. **镜像时机**：**部署成功后再镜像**（`needs: deploy`）——企业仓库上看到的就是已上线的那版。
3. **企业仓库 Actions**：**直接关闭**，从根上断掉双部署，也不再跑无用的 build + 5 个 dry-run。
4. **执行方式**：授权会话用 `gh` 全自动配置。

## 三、架构

```
本地/各会话 push ──► pan-nie/whizzzest.com（权威）
                          │  CI: check → deploy（5 个 Worker）
                          └─► mirror job（needs: deploy 成功）──► Whizzzest/whizzzest.com（只读镜像）
                                                             （Actions 已关，不再触发任何 CI）
```

- 镜像 job 位于 [.github/workflows/deploy.yml](../.github/workflows/deploy.yml) 的同名 workflow 内、`needs: deploy`；
- 守卫 `if: github.repository == 'pan-nie/whizzzest.com'`：**同一份文件被镜像到企业仓库后也会跑**，靠这行自动跳过 → 防回环；
- `fetch-depth: 0`（浅克隆推不动，GitHub 会回 `shallow update not allowed`）；
- 只推 `git push org HEAD:refs/heads/main`，**不用 `--mirror`**——`--mirror` 会连带强推/删除企业仓库上独有的分支与标签，风险大于收益；
- host key 用 `https://api.github.com/meta` 公布的 GitHub ed25519 固定值写进 `known_hosts`，不用 `ssh-keyscan`（少一个中间人面）。

## 五、日常运维

**正常情况**：什么都不用做——push main → CI 部署成功 → 自动镜像。可在 Actions 里看 `Mirror to Whizzzest/whizzzest.com` job。

**手动补推一次**（比如镜像 job 挂了、或本地临时要同步）：

```bash
git push git@github.com:Whizzzest/whizzzest.com.git main
```

**对账（两库是否一致）**：

```bash
git ls-remote origin refs/heads/main
git ls-remote https://github.com/Whizzzest/whizzzest.com.git refs/heads/main
git rev-parse HEAD              # 三者应完全相同
```

**只推进了文档提交、没触发部署？** 不会：`mirror` 是 `needs: deploy`，而 `deploy` job 在 push main 时无论改什么都跑（build + 部署），所以文档提交同样会镜像。

**PR 事件**：`deploy` 与 `mirror` 都不会跑（守卫里排除了 `pull_request`）。

**给我换 token**（方案 A 的 fine-grained PAT 到期时）：New fine-grained token（Resource owner `Whizzzest`、仅 `Whizzzest/whizzzest.com`、`Contents: RW` + `Workflows: RW`）→ `gh secret set ORG_MIRROR_TOKEN -R pan-nie/whizzzest.com`。**换 token 不需要改代码**（mirror job 只读这个 secret），也没有停摆窗口。

**临时停掉镜像**：`gh variable set ORG_MIRROR_ENABLED -R pan-nie/whizzzest.com --body false`（job 变 skipped，CI 不红）；恢复同理改回 `true`。

**换 Deploy Key**（仅在回到 SSH 方案时才需要）：`gh repo deploy-key delete <id> -R Whizzzest/whizzzest.com` → 重新 `ssh-keygen` → `gh repo deploy-key add ... --allow-write` → `gh secret set ORG_MIRROR_SSH_KEY -R pan-nie/whizzzest.com < 私钥`；注意必须先打开组织策略 `deploy_keys_enabled_for_repositories`，且**该方案对 `.github/workflows/**` 的改动无效**（§8）。

**改用路径 B（给 gh 加 workflow scope）**：`git remote` 与凭据都换回 HTTPS + `ORG_MIRROR_TOKEN` 形式即可，token 换成 gh 的 OAuth token——但注意它带 `repo`，能访问你所有仓库。

**将来把权威挪到企业仓库**：参照本方案 §3 反向做一遍即可——`origin` 换成企业仓库、`gh secret set CLOUDFLARE_API_TOKEN -R Whizzzest/whizzzest.com`（以及其余 secret）、把 mirror job 的 `if` 守卫与目标仓库对调、恢复企业仓库 Actions。

**回滚镜像**（完全停掉同步）：删掉 `deploy.yml` 里的 `mirror` job 并 push；企业仓库代码保持当时状态，不影响线上（部署始终只在 pan-nie 仓库发生）。

## 六、已知副作用与限制

1. **企业仓库不再跑 push/PR 的 workflow**（业主拍板，实测：禁用后两次手工推送 `0770401`、`5deb5fb` 均未触发任何运行）。但 **Dependabot 安全更新不受 Actions 开关约束**：该仓库仍有 open PR（如 `#2 app/dependabot: chore(deps): bump the npm_and_yarn group`），镜像仓库上这类 PR 永远合不了、纯噪音——嫌吵可在该仓库 Settings 里关掉 Dependabot security updates（本方案不代做，属安全姿态取舍）。
2. **镜像只同步 `main` 分支与当时已推的提交**：PR 分支、标签不同步（当前仓库也没有 tag）。将来若要同步 tag，在 mirror job 里加一行 `git push org --tags`。
3. **镜像提交的 author 不变、push 者变成 Deploy Key**：企业仓库上显示为 `Whizzzest/whizzzest.com` 的部署密钥推送，不是个人账号。
4. **组织策略是组织级的**：打开 Deploy Key 后，组织内其他仓库也能加（这是路径 A 的代价，业主已知并拍板）。
5. **企业仓库的 `deploy.yml` 依然存在**（镜像内容的一部分）：只要不在企业仓库配 `CLOUDFLARE_API_TOKEN` 且 Actions 关闭，它永远不会执行。

## 八、已知阻塞：Deploy Key 推不了 `.github/workflows/**`（2026-10-14 实测）

首次自动化运行（commit 0770401，CI run 38536830057）**mirror job 失败**，日志原文：

```
! [remote rejected] HEAD -> main (refusing to allow an OAuth App to create or update
  workflow `.github/workflows/deploy.yml` without `workflow` scope)
```

本地用同一把 Deploy Key 私钥复现了完全相同的拒绝 —— 即 **GitHub 禁止 Deploy Key 修改 workflow 文件**
（与 PAT 缺 `workflow` scope 同一条规则）。本次首次同步之所以成功，是因为当时那 22 个提交里没有 workflow 改动。

**影响**：只要某个提交动了 `.github/workflows/**`，镜像必失败。这不是偶发，是设计性限制。

**当前处置（临时）**：mirror job 加总闸 `vars.ORG_MIRROR_ENABLED == 'true'`（默认关，job 显示 skipped 而非红），
三库已用个人 SSH 身份手工对齐到 `0770401`。凭据换好后 `gh variable set ORG_MIRROR_ENABLED --body true` 一处开闸。

**凭据三选一（待业主定）**：

| | A. fine-grained PAT（推荐） | B. 给 gh 加 workflow scope | C. 继续 Deploy Key，镜像排除 CI 配置 |
| --- | --- | --- | --- |
| 做法 | 业主建 token：仅授权 `Whizzzest/whizzzest.com`，`Contents: RW` + **`Workflows: RW`** → 存 secret `ORG_MIRROR_TOKEN` → mirror job 改 HTTPS | 业主执行 `gh auth refresh -h github.com -s workflow`（浏览器确认一次）→ 取其 token 存 secret | 保持现状；镜像**不带** `.github/workflows` 改动（需要在 CI 里重写提交，复杂度高；且企业仓库的 workflow 文件永远停在旧版） |
| 权限面 | **最窄**：单仓库、只这两项权限 | 最广：OAuth token 带 `repo` = 你**所有**仓库读写 | 无新凭据 |
| 寿命 | 有有效期（到期需换，方案 §5 有步骤） | 随 gh 重新授权轮换 | 永久 |
| 我方需额外做的 | mirror job 换成 HTTPS + token 头 | 同左 | 改写提交树的镜像逻辑（不推荐） |

> 若最终改走 A/B（不再用 Deploy Key）：应删除企业仓库的 Deploy Key `166402039`，并把组织策略
> `deploy_keys_enabled_for_repositories` 改回 `false`（恢复原安全姿态）——方案 §4 的 1、2 两项作废，secret
> `ORG_MIRROR_SSH_KEY` 一并删除。
